Multi-Tab Worker Spawning

Let the coordinator spill workers into new Herdr tabs when the current tab is physically full. Minimal, explicit, no auto-topology. One new tool, one new param, one new signal.

01

Problem

Picode pins all workers to the coordinator's tab. Three hardcoded guards in spawn.ts reject panes outside the current tab.

HARDCODED SAME-TAB GUARDS
// getSplitTarget — line ~194
if (tabId !== currentTabId) continue;

// findEmptyPane — line ~433
if ((pane.tab_id) !== currentTabId) continue;

// computeDirection — line ~291
if ((pane.tab_id) !== currentTabId) continue;
PHYSICAL CEILING

Herdr's pane split refuses when the result drops below MIN_PANE_RATIO = 20% of the workspace dimension.

After ~4–5 panes, every split candidate falls below threshold → getSplitTarget falls back to the coordinator pane → next spawn shrinks the command center or fails. Coordinator dead-ends with no recovery path.

REAL CEILING coordinator + 4 workers ≈ 5 panes in a 2×3-ish grid. That matches the physical limit, not an arbitrary number. A 4K monitor may fit 6; a laptop may fit 3. The threshold adapts.

02

Goal

Let the coordinator keep spawning workers past the single-tab ceiling by opening new tabs. Minimal, explicit, no auto-topology inference.

NON-GOAL

Auto-deciding tab topology from task type ("frontend tab vs backend tab"). That's the overkill version — coordinator shouldn't guess.

NON-GOAL

Cross-workspace spawning. Stay in current workspace; only add tabs within it.

NON-GOAL

Changing envelope wire format, state file layout, or existing tool names.

NON-GOAL

Making the coordinator manage pane geometry. Herdr does geometry; picode does mailboxes.

03

Design Decisions (made, not asked)

D1

Trigger = physical fullness, not pane count

New tab opens when spawn_worker cannot find a split target ≥ MIN_PANE_RATIO in the requested tab — not when pane count hits 4. Pane count is noisy (dead panes, manual splits, gaps); physical fullness is the real signal the tool already computes. "4 per tab" is a soft target in the prompt, not a hardcoded constant.

D2

spawn_worker gains optional tab param

tab: Type.Optional(Type.String({
  description: "Tab ID to spawn in (e.g. w1:t3). Default: current tab. When the requested tab is full, returns tab_full=true instead of splitting — call picode_tab_create then retry."
}))

Zero behavior change when omitted. Existing flows unaffected.

D3

New tool picode_tab_create

Coordinator has no bash — needs a tool to open tabs. Returns { tab_id, root_pane_id }. The root pane is not a worker — it's an empty shell the coordinator later splits via spawn_worker(tab=<tab_id>). We do NOT auto-spawn a worker into it; explicit is better. 

picode_tab_create(label?, cwd?, focus?)
// label  — tab label (e.g. "frontend"). Default: herdr assigns.
// cwd    — working dir for root pane. Default: current cwd.
// focus  — focus the new tab. Default: false (keep coordinator focused).
// → { ok, tab_id, root_pane_id, label }
D4

spawn_worker returns tab_full signal — does NOT auto-open

When the requested tab has no valid split target and no empty pane, returns: 

{ "ok": false, "tab_full": true, "tab_id": "w1:t1",
  "message": "Tab w1:t1 is full — no pane ≥20% to split. Call picode_tab_create() then retry." }

Coordinator logic stays dumb: try spawn → tab_full? → picode_tab_create → retry with new tab_id. Two steps, no orchestration explosion. Tool never silently opens a tab — coordinator decides. Auto-open hides the decision from coordinator and human; explicit retry makes tab creation observable + journalable.

D5

picode_panes — no change

Already groups by tab in text output and includes tab_id in details.panes[]. Confirmed by reading panes.ts.

D6

cleanup_panes / pane_read — no change

Target by pane_id (globally unique). Bulk scan is pane list --workspace (all tabs). Tab-agnostic. Confirmed.

D7

picode_purge — no change

Operates on .picode/picodes/<id>/state.json dirs, not panes. Tab irrelevant.

D8

Herdr listener — no change

Tracks by pane_id, filters by workspace_id. Tab irrelevant. Workers in other tabs still get tracked + reported.

D9

Coordinator prompt — add short "Tabs" section

### Tabs (when the tab is full)

Workers spawn in your current tab by default. A tab fits ~4–5 panes in a grid
before splits get too small. When a tab is full, spawn_worker returns
tab_full=true instead of forcing a bad split.

Flow:
1. spawn_worker(role="builder") → { ok: false, tab_full: true, tab_id }
2. picode_tab_create(label="workers-2") → { tab_id, root_pane_id }
3. spawn_worker(role="builder", tab="<new tab_id>") → spawns in new tab

Do not pre-create tabs speculatively. Open one only when a spawn returns tab_full.
Two tabs is typical for a large job; three is rare. Cleanup is unchanged —
cleanup_panes() scans the whole workspace across all tabs.
D10

picode_tab_create is coordinator-only

Same guard as spawn_worker. Workers delegate up, not down. Keeps hierarchy flat.

D11

Tab label validation

Max 32 chars, [a-zA-Z0-9_-] only. Prevents shell injection via herdr tab rename. Same pattern as validateRole.

D12

New tab's root pane is NOT tracked as a worker

picode_tab_create returns root_pane_id but does NOT call trackPane(). Root pane has no agent — tracking it would inject spurious close events. Only spawn_worker tracks panes it actually launches agents into.

src/tools/tab-create.ts

export function registerTabCreateTool(pi, store) {
  pi.registerTool({
    name: "picode_tab_create",
    parameters: Type.Object({
      label: Type.Optional(Type.String()),
      cwd:   Type.Optional(Type.String()),
      focus: Type.Optional(Type.Boolean()),
    }),
    async execute(_id, params) {
      if (store.role !== "coordinator") return err("coordinator-only");
      const ws = process.env.HERDR_WORKSPACE_ID;
      if (!ws) return err("HERDR_WORKSPACE_ID not set");
      // validate label (max 32, [a-zA-Z0-9_-])
      // herdr tab create --workspace $ws --no-focus [--label ..] [--cwd ..] [--focus]
      // → { ok, tab_id, root_pane_id, label }
      // NOTE: does NOT trackPane(root_pane_id) — no agent there
    }
  });
}

--no-focus default keeps coordinator's tab focused. Pass --workspace explicitly so tab lands in same workspace. shellQuote extracted to shared.ts (§4.5).

09

Resolved Questions (defaults chosen)

Auto-spawn worker into new tab?

No. Returns empty root pane. Explicit spawn_worker(tab=...). Explicit > implicit — separate observable steps. (D3)

Cap number of tabs?

No hard cap. Physics + cleanup enforce it. Prompt: "two typical, three rare." Hard cap blocks legit large jobs. (D1)

Filter picode_panes by tab?

Not now. Already groups by tab + includes tab_id in details. Coordinator filters JSON itself. Add tab filter later if needed. (D5)

/picode-tabs slash command?

Defer. CLI could get tabs subcommand later. Not needed for agent flow. (§4.6)

Journal tab creation?

No. Tabs are herdr UI state, not picode protocol state. Tool call shows in coordinator session log naturally. (D9)

Coordinator's own tab closed by user?

Out of scope. Coordinator-death scenario, existing lifecycle/purge logic. Multi-tab doesn't change it.

Workers spawn sub-workers in new tabs?

No. Both tools coordinator-only. Workers delegate up, not down. Flat hierarchy. (D10)
