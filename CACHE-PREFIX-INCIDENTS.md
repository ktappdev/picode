# Cache-prefix incident history

A short index and recurrence guide for coordinator prompt-cache incidents. This complements the [cache-diagnostics runbook](CACHE-DIAGNOSTICS.md), which owns the tracker schema, record interpretation, known limits, and decisive experiment. Start there for commands and field definitions; this file records what the incidents taught us and how to classify the next warning.

## Causes and evidence

### 1. Continuation requests did not reconstruct the prompt consistently

Scout's pi-better-models analysis identified two interacting head-shape candidates:

- **Third-party forced-prompt reshape (80–85% confidence).** The advertised pi-subagents block added about 615 tokens, and pi-cache-optimizer reordered about 11 tokens. Those changes were outside Picode's own leading-prompt reconstruction. `CACHE-DIAGNOSTICS.md` records this blind spot explicitly: [`fullPromptHash` cannot see forced-prompt appends](CACHE-DIAGNOSTICS.md#known-limits--what-this-trace-cannot-prove).
- **Pi section stripping on continuation (95% confidence).** A continuation could persist a `{picode: null}` section strip, making its prompt differ from a prompt-driven run even when Picode's own computed prompt had not changed. The exact transport distinction and its mechanics are captured in the original fix commit `bdecb4b` and merged to main in `9608399`.

The warning was not proof that the next tool call caused a cache miss. The trace was correlational (97% confidence); compare the request and response fingerprints before attributing cause. In particular, an unchanged Picode `fullPromptHash` cannot rule out a forced block added after Picode's reconstruction.

### 2. The worker digest had a timer-driven field

Before `a8219d6`, `contextAgeMinutes` was rounded in `src/core/worker-ledger.ts:255`; `humanAge` rendered minute counts in `src/core/worker-ledger.ts:287-293`, and `formatWorkerDigest` put the result into stopped-worker rows at `:311`. Thus an unchanged stopped worker could change the digest every minute. Scout hash-verified this class of mover in 6/6 comparisons. The volatility ranking was age, `leftUnverified`, liveness, area, HEAD freshness, then row order.

Age was the chronic no-event churn. Handoffs, liveness, area, HEAD freshness, and ordering remain untouched; inspect their actual changes rather than attributing them to the timer-driven age issue. The separate section-granularity amplification—rules and roster previously sharing a section—is already covered in the diagnostics runbook and was fixed by `e272dc5`.

Residual upstream Pi limitation: when an event arrives while Pi is already streaming, `sendUserMessage` queues it as a continuation, so it necessarily remains a continuation run and does not invoke `before_agent_start`. Picode funnels the event through `inbox.inject()` to share gate/coalescing behavior, but cannot make that streaming continuation prompt-driven without an upstream Pi change.

## Recurrence runbook: first 10 minutes

1. **Capture the exact warning and context.** Record its full text, timestamp, provider/model, Pi version, Picode commit, role, session, and the preceding worker/tool event. A warning that precedes a tool call is not caused by that later call merely because it is nearby in the transcript.
2. **Open the matching Picode trace.** Follow [“What the tracker records”](CACHE-DIAGNOSTICS.md#what-the-tracker-records) for the hashed per-picode path and record definitions. Do not paste raw prompt or message text into this note; the tracker intentionally stores fingerprints only.
3. **Compare adjacent prompt and payload records.** Start with `fullPromptHash`, `workerDigestHash`, `picodeWithoutWorkersHash`, `payloadHash`, `payloadChanges`, `instructionsHash`/`instructionsChars`, and response `reBilledTokens`, `cacheReadAdvanced`, `idleMs`, and `previousRequest`. Check `promptChanges` too, but do not treat it as a causal verdict.
4. **Classify the delta.**
   - **Likely Picode roster change:** `workerDigestHash` changes, and the rendered row explains it (worker lifecycle or age bucket). After both fixes, a roster update may still change the section; it should not recreate the old continuation-only `{picode: null}` strip. Judge the cost from `payloadChanges` and provider counters, not from the warning text alone.
   - **Likely external/head mutation:** Picode's reconstructed hashes stay the same or explain only a small digest change, but actual payload/instructions fingerprints show a change at the head (for example, `request message 0` or provider instructions). Check extension ordering and forced-prompt behavior, especially the pi-subagents advertised block and pi-cache-optimizer reorder. The diagnostics blind-spot bullet explains why `fullPromptHash` alone misses this.
   - **Likely ordinary section update:** Picode's worker digest changes and the payload delta is appended after the existing prefix; `cacheReadAdvanced` progresses and the re-bill is near a small delta or normal provider block granularity, not the whole conversation. Use [“Interpreting a reading”](CACHE-DIAGNOSTICS.md#interpreting-a-reading) for the tracker-specific distinctions.
   - **Not enough evidence:** `payloadChanges: null`, a missing prior request, a Pi-version boundary, or a change beyond the tracker's first eight payload segments. Say so; do not infer an unchanged request from equal reconstructed hashes.
5. **Check the age bucket and event history.** For a stopped row, compare its `contextAgeMinutes` with the bucket rendered by `humanAge`; a minute tick inside the same bucket should not alter the digest. A bucket crossing or changes to `leftUnverified`, `live`, `area`, HEAD freshness, or row order can still change it. Verify the actual digest before calling it a regression.
6. **If the request really re-billed the full prefix, preserve a before/after pair.** Save adjacent prompt/payload/response records, relevant warning lines, Pi and extension versions, and the exact transition. Then rerun the controlled worker-lifecycle experiment in [`CACHE-DIAGNOSTICS.md`](CACHE-DIAGNOSTICS.md#the-decisive-experiment) before changing prompt assembly.

## Open items

- **Mid-run continuation gap.** `sendUserMessage` uses the safe prompt-driven path for idle injections, but when Pi is already streaming, injections queue as steer/follow-up continuations. Those continuations do not rerun `before_agent_start`. Pi needs to diff continuation runs against the last prompt-driven options; track the upstream change before claiming this class fully closed.
- **Legacy Pi cache cost.** Pi versions without structured prompt sections still use Picode's forced-prompt fallback at `src/lifecycle.ts:853`. Correctness is preserved, but repeated injection-driven prompt runs can still rebuild the leading prompt and incur cache cost.
- **External prompt transformations.** Picode's tracker cannot reconstruct arbitrary later-extension forced-prompt appends/reorders. Keep the payload/instructions fingerprints and exact extension versions whenever the warning recurs.
- **Live confirmation with workers.** The earlier cache trace was workerless and could not exercise roster movement. Capture a post-fix coordinator trace with workers; confirm a digest update is not followed by a whole-conversation re-bill. See [`CACHE-DIAGNOSTICS.md`’s “What would close it”](CACHE-DIAGNOSTICS.md#what-would-close-it).
- **Known test failure.** `test/unit.test.ts:2371` (“a run that changed state still journals”) fails identically on base; it is unrelated to digest rendering and remains untouched.
